4.4 温度缩放与 softmax 采样：完整数学推导

这一页解释 logits 怎么变成一个采样，以及 temperature 到底在动什么。 它的重要性在于：self-consistency 采样出不同答案这件事，完全依赖这里的机制。没有温度控制，同一个 prompt 采样 8 次会得到 8 个几乎一样的答案，投票就没有意义了。

一、生成下一个 token 的三个步骤

用原文的例子：ex_prompt = "The capital of Germany is"，作者把流程拆成 figure 4.6 的三步。

  1. 编码：文本转 token ID。原文得到 [785, 6722, 315, 9856, 374]，长度 5。
  2. 前向传播：得到 logits，形状 [1, 151936]。151,936 是 Qwen3 0.6B 的词表大小。
  3. 选一个：torch.argmax(logits) 给出 19846，即 " Berlin"。
with torch.inference_mode():
    next_token_logits = model(input_token_ids)[:, -1]
# 形状 [1, 151936]；[:, -1] 取最后一个位置的预测（下一个 token 的分布）
max_token_id = torch.argmax(next_token_logits)  # 19846
[:, -1] 为什么这样取：输入 5 个 token，模型输出 5 行预测（[5, 151936]），但只有最后一行对应「下一个新 token」。这就是前面 6.8 节讲的因果掩码错位。

二、logits 是什么，为什么不能直接用

logits 是输出层给出的、每个词表条目的一个未归一化的分数，实测范围约 \(-8\) 到 \(20\)，" Berlin" 大约是 20。

它们有两个问题，所以不能直接当概率用：

  1. 不是概率：可以取负数，且不保证总和为 1。概率必须非负且和为 1。
  2. 无法直接采样：因为有负值，你不能写 random() * sum(logits) 这种代码来做按比例抽样。

三、softmax：把 logits 变成概率

\[ \text{softmax}(\mathbf{z})_i = \frac{\exp(z_i)}{\sum_{j=1}^{|V|}\exp(z_j)}, \qquad \sum_i \text{softmax}(\mathbf{z})_i = 1 \] 
rescaled_logits = scale_logits_by_temperature(next_token_logits, 5.0)
next_token_probas = torch.softmax(rescaled_logits, dim=-1)
print("Probability sum:", torch.sum(next_token_probas))  # 1.0000

3.1 为什么要减最大值（数值稳定）

\(\exp(z_i)\) 里的 \(z_i\) 可以是 20，\(\exp(20) \approx 4.85 \times 10^8\)。如果某个 logit 是 100，\(\exp(100) \approx 2.7 \times 10^{43}\)——float32 的上限约 \(3.4 \times 10^{38}\)，直接溢出。

标准做法是分子分母同时减去最大值 \(m = \max_j z_j\)：

\[ \frac{\exp(z_i - m)}{\sum_j \exp(z_j - m)} \;\; \xrightarrow{\; \times e^{-m}\;} \;\; \frac{\exp(z_i)}{\sum_j \exp(z_j)} \]

数学上完全等价（分子分母同乘 \(e^{-m}\)），但所有指数的输入都变成 \(\le 0\)，\(\exp\) 的结果必然在 \((0, 1]\) 区间，永远不会溢出。PyTorch 的 torch.softmax / torch.log_softmax 内部都做了这件事。

这解释了一个 API 设计

为什么不写 torch.log(torch.softmax(x))？因为那样要过两次浮点：先 softmax 可能算出极小的数（比如 \(10^{-40}\)，bfloat16 下就是 0），再取 log 就得到 \(-\infty\)。torch.log_softmax 在 log 空间里做数值稳定版本，一次到位。

原文在 5.5 节也提到：In practice, I prefer to use the torch.softmax function because it has some additional numerical stability improvements，并且有 Warning 说 softmax 配 sum、log_softmax 配 prod 是「技术上可行但数学上错误」的组合。

四、温度缩放：动的到底是什么

def scale_logits_by_temperature(logits, temperature):
    if temperature <= 0:
        raise ValueError("Temperature must be positive")
    return logits / temperature
\[ z_i^{(T)} = \frac{z_i}{T}, \qquad P_T(i) = \text{softmax}\!\left(\frac{\mathbf{z}}{T}\right)_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)} \]

关键在于原文指出的这一点：重要的不是某个 logit 的绝对高度，而是 logit 之间的差异如何变化。

4.1 温度如何改变「差距」

设两个竞争 token 的 logit 差为 \(\Delta = z_1 - z_2\)。它们概率之比是：

\[ \frac{P(1)}{P(2)} = \frac{\exp(z_1/T)}{\exp(z_2/T)} = \exp\!\left(\frac{z_1 - z_2}{T}\right) = \exp\!\left(\frac{\Delta}{T}\right) \]

所以：

温度对 \(\Delta\) 的作用概率比行为
\(T = 1.0\)不变\(e^{\Delta}\)原始分布
\(T < 1.0\)\(\Delta\) 放大\(e^{\Delta/T}\)，更大更尖锐（sharper），更确定
\(T > 1.0\)\(\Delta\) 压缩\(e^{\Delta/T}\)，更小更平坦（flatter），更随机
用原文的实测数字

" Berlin"（logit ≈ 20）在 T = 5.0 时概率是 0.0003（0.03%）；在 T = 0.5 时概率是 0.3398（34%），其他 token 全部趋近 0。

也就是说，把温度从 5 降到 0.5，那个 token 的概率放大了一千多倍。这就是「sharper」的具体含义。

4.2 极限情况

\[ T \to 0^+ \;\Longrightarrow\; P(i) \to \begin{cases} 1 & \arg\max_j z_j = i \\ 0 & \text{otherwise} \end{cases} \qquad T \to \infty \;\Longrightarrow\; P(i) \to \frac{1}{|V|} \]

原文的实际演示很有说服力：T = 5.0 下采样 1 个 token，得到的是 65094，即 " mistress"——在「德国的首都是」这个语境下完全说不通。就是这么被随机出来的。

这就是 multinomial 的意义

如果用 argmax（贪心解码），温度完全不起作用——argmax 只看排名，不看分值。所以原文的生成函数里是 if temperature is None or temperature == 0.0: next_token = torch.argmax(...)，走另一条分支。

五、multinomial 采样

torch.manual_seed(123)
print("Sampled token:", torch.multinomial(next_token_probas.cpu(), num_samples=1))

\(\text{multinomial}(\mathbf{p}, k)\) 的定义：按概率 \(p_i\) 抽取 \(k\) 次，有放回。数学上等价于对每个 \(i\) 独立做一次 categorical 采样，\(\Pr(\text{抽到 } i) = p_i\)。

所以整个采样链是：

\[ \text{logits} \xrightarrow{\ \div T\ } \frac{\mathbf{z}}{T} \xrightarrow{\ \text{softmax}\ } \mathbf{P} \xrightarrow{\ \text{multinomial}\ } y_t \]
关于 .cpu()：原文把采样放在 CPU 上做，并说明原因——torch.multinomial() 在 CUDA 和 MPS 上结果可能不同（作者在 PyTorch 2.9 上观察到大 num_samples 时甚至会崩溃）。放 CPU 保证可复现。

六、为什么这套机制是 self-consistency 的前提

第 4.6 节的 self-consistency 要「同一个 prompt 生成 N 个不同答案，然后对最终答案投票」。它需要：

  1. 每次采样足够随机，否则 N 个答案完全相同，投票退化为 \(N\) 选 1 → 温度要大于 0（原文用 0.8）。
  2. 但又不能太随机，否则全是废话。top-p 过滤（下一页详解）负责砍掉低概率 token。
  3. 各次采样互相独立，所以可以并行（有多 GPU 的话），用户等待时间不增加。

原文的措辞：Since the multiple answers generated with this technique are independent of each other, this can be implemented through parallel sampling。

温度的选择是个权衡

T 太小 → 每次采样结果一样，self-consistency 退化成单次生成，没有任何增益。
T 太大 → 答案全是噪声，投票结果比单次生成还差。
0.8 是这类数学任务上的经验值，既保证多样性又不至于失控。
